# Отслеживание обработки СЭМД в Онкор

Основной рекомендуемый способ разбирать движение СЭМД — использовать Онкор API.

Доступ к базе `catcher` лучше рассматривать как вспомогательный диагностический сценарий. Он полезен, когда на руках есть только технический идентификатор сообщения из `catcher`, например `internal_message_id` или `external_message_id`, и по нему нужно найти связанную задачу обработки СЭМД в Онкор.

Если на стороне МИС известны глобальные идентификаторы самого СЭМД (`set_id`, `id`, `version_number`), предпочтительно сразу использовать метод `cda/search`, без обращения к базе `catcher`.

## Что происходит при обработке нового СЭМД

После передачи нового СЭМД в Онкор создаётся задача обработки `CdaTask`.
Эта задача отражает полный путь СЭМД: от приёма и проверки документа до отправки результата во внешнюю систему.

На этапе обработки Онкор выполняет привязку СЭМД к пациенту.
Новый СЭМД может:

1. найти существующего пациента по ФИО и СНИЛС;
2. создать нового пациента, если подходящий пациент не найден.

Это важно учитывать при разборе результата обработки.
Если пациент найден, в ответе API будет заполнено поле `patient_id`, а в `cda_task_log` можно увидеть сообщение о том, как именно был найден пациент, например `INFO: пациент найден по СНИЛС`.

Если пациент не найден и Онкор создаёт нового пациента, в `patient_id` будет указан идентификатор созданной записи пациента, а детали выполнения будут отражены в `cda_task_log`.

Таким образом, при анализе нового СЭМД можно увидеть не только общий статус задачи `cda_task_status`, но и:

* `patient_id` — к какому пациенту был привязан СЭМД;
* `cda_task_log` — детали поиска/создания пациента;
* `cda_task_step` — на каком этапе сейчас находится обработка СЭМД;
* `rc_cda_id` и `rc_sms_id` — какие входящие и исходящие объекты были созданы в Онкор.

## Как `set_id`, `id` и `version_number` представлены в CDA

В API идентификаторы СЭМД передаются в JSON-формате, но исходно они берутся из CDA-документа.

В CDA эти значения представлены в элементах `setId`, `id` и `versionNumber` внутри `ClinicalDocument`:

```xml
<ClinicalDocument>
    ...
    <id
        root="1.2.643.5.1.13.13.12.2.25.2260.100.1.1.51"
        extension="5048d857-206e-aa9b-e063-04f21aacd892"/>

    <setId
        root="1.2.643.5.1.13.13.12.2.25.2260.100.1.1.50"
        extension="5048d857-206e-aa9b-e063-04f21aacd892"/>

    <versionNumber value="1"/>
    ...
</ClinicalDocument>
```

При вызове `cda/search` эти же значения передаются в объекте `cda`:

* `ClinicalDocument/setId/@root` → `cda.set_id.root`;
* `ClinicalDocument/setId/@extension` → `cda.set_id.extension`;
* `ClinicalDocument/id/@root` → `cda.id.root`;
* `ClinicalDocument/id/@extension` → `cda.id.extension`;
* `ClinicalDocument/versionNumber/@value` → `cda.version_number`.

`setId` обычно используется как идентификатор набора версий документа.
`id` идентифицирует конкретный экземпляр документа.
`versionNumber` указывает версию документа внутри набора версий.

Поэтому, если на стороне МИС есть исходный CDA, для поиска задачи обработки СЭМД в Онкор не требуется обращаться к базе `catcher`: достаточно взять эти значения из CDA и передать их в `cda/search`.

## Рекомендуемый подход: использование API без базы `catcher`

На стороне МИС обычно известно, с какими именно идентификаторами был передан СЭМД.
В этом случае доступ к базе `catcher` не требуется: достаточно метода API `cda/search`.

Метод `cda/search` удобно использовать, когда нужно найти задачу обработки СЭМД по глобальным идентификаторам самого документа: `set_id`, `id` и `version_number`.

Результат будет иметь тот же формат, что и у метода `cda/get`, поэтому дальнейший анализ выполняется по тем же полям: `cda_task_status`, `cda_task_step`, `patient_id`, `rc_cda_id`, `rc_sms_id` и `cda_task_log`.

### `cda/search` — поиск СЭМД по `id`, `set_id`, `version_number`

Варианты поиска:

1. только `set_id`: список всех `CdaTask`, совпавших по `set_id`;
2. `set_id` + `version_number`: список всех `CdaTask`, совпавших по `set_id` и отфильтрованных по `version_number`;
3. `set_id` + `version_number: latest`: список всех `CdaTask`, совпавших по `set_id`, с последней версией;
4. `set_id` + `id`: список всех `CdaTask`, совпавших по `set_id` и отфильтрованных по `id`;
5. `set_id` + `id` + `version_number`: список всех `CdaTask`, совпавших по `set_id` и отфильтрованных по `id` и `version_number`;
6. только `id`: список всех `CdaTask`, совпавших по `id`.

Пример:

```http request
POST {{ONCOR_API_HOST}}/api/1.0/json/cda/search
X-Oncor-API-Token: {{ONCOR_API_TOKEN}}
Content-Type: application/json

{
    "cda": {
        "set_id": {
            "root": "1.2.643.5.1.13.13.12.2.25.2260.100.1.1.50",
            "extension": "5048d857-206e-aa9b-e063-04f21aacd892"
        },
        "id": {
            "root": "1.2.643.5.1.13.13.12.2.25.2260.100.1.1.51",
            "extension": "5048d857-206e-aa9b-e063-04f21aacd892"
        },
        "version_number": "1"
    }
}
```

Результат будет того же формата, что и для метода `cda/get`, но массив `result` в ответе может быть пустым или содержать несколько объектов.

            "cda": {
                "set_id": {
                    "root": "1.2.643.5.1.13.13.12.2.25.2260.100.1.1.50",
                    "extension": "5048d857-206e-aa9b-e063-04f21aacd892"
                },
                "id": {
                    "root": "1.2.643.5.1.13.13.12.2.25.2260.100.1.1.51",

## `cda/get` — запрос статуса задачи обработки СЭМД

Метод `cda/get` используется, когда уже известен идентификатор задачи обработки СЭМД в Онкор — `cda_task_id`.

Такой идентификатор может быть получен из ответа `cda/search`, из интерфейса Онкор или, в менее предпочтительном диагностическом сценарии, из поля `semd.rc_id` таблицы `semd` базы `catcher`.

Если значение хранится с символом `#`, например `#3240:3369361`, то в запросе API используется значение без `#`: `3240:3369361`.

### Запрос

```http request
GET {{ONCOR_API_HOST}}/api/1.0/json/cda/get?id=3240:3369361
X-Oncor-API-Token: {{ONCOR_API_TOKEN}}
```

### Ответ

```json
{
    "result": [
        {
            "cda_task_id": "#3240:3369361",
            "patient_id": "#71:16439",
            "rc_cda_id": "#3029:3149721",
            "rc_sms_id": "#2180:3275155",
            "cda": {
                "set_id": {
                    "root": "1.2.643.5.1.13.13.12.2.25.2246.100.1.1.50",
                    "extension": "510d77f8-bbe6-24b9-e063-04f21aaccca7"
                },
                "id": {
                    "root": "1.2.643.5.1.13.13.12.2.25.2246.100.1.1.51",
                    "extension": "510d77f8-bbe6-24b9-e063-04f21aaccca7"
                },
                "version_number": "1"
            },
            "cda_task_status": "PROCESSING",
            "cda_task_step": "SENDING_TO_VIMIS",
            "cda_task_log": [
                "INFO: пациент найден по СНИЛС",
                "INFO: Rc: #2180:3275155 was sent. Internal message id = '0618c85f-6a02-49a8-848f-3a1f8a713ce4'"
            ]
        }
    ]
}
```

### Как читать ответ

_Массив вместо объекта в `result` является особенностью универсального преобразования protobuf в JSON и не связан с логикой метода `cda/get`._

#### Основные поля ответа

* `cda_task_id`: идентификатор задачи обработки СЭМД в Онкор.
* `cda_task_log`: человекочитаемый журнал выполнения задачи. По нему можно понять, какие действия уже были выполнены: например, был ли найден пациент, был ли создан исходящий объект и был ли СЭМД отправлен дальше.
* `patient_id`: идентификатор пациента, к которому привязан СЭМД. Может относиться как к ранее существовавшему пациенту, так и к пациенту, созданному при обработке нового СЭМД.
* `rc_cda_id`: идентификатор входящего СЭМД. Может использоваться как для API, так и для формирования ссылки в браузере.
* `rc_sms_id`: идентификатор исходящего СЭМД. Может использоваться как для API, так и для формирования ссылки в браузере.
* `cda`: объект с глобальными идентификаторами СЭМД. Может использоваться для работы с ВИМИС.
* `cda_task_status`: общий статус задачи обработки СЭМД:
    * `PENDING`
    * `PROCESSING`
    * `DONE`
    * `ERROR`
* `cda_task_step`: текущий шаг задачи обработки СЭМД:
    * `VALIDATION_ON_ONCOR`
    * `ONCOR_ACCEPTED`
    * `SENDING_TO_VIMIS`
    * `VIMIS_ACCEPTED`

Для формирования ссылки в браузере нужно подставить значение поля без `#` после `/ui-orid/` в адрес сервера.
Например, для `#71:16439` ссылка будет такой: https://oncor.pkmiac.ru/ui-orid/71:16439

## Вспомогательный сценарий: таблица `semd` базы `catcher`

Таблица `semd` базы `catcher` может использоваться для первичного отслеживания статуса СЭМД, который был передан в обработку.
Этот способ стоит рассматривать как вспомогательный: он нужен не для основного разбора движения СЭМД, а для перехода от технических идентификаторов `catcher` к задаче обработки в Онкор.

Таблица полезна в ситуациях, когда известен только `internal_message_id` или `external_message_id`, а нужно найти связанную с ним задачу обработки СЭМД в Онкор.

```postgresql
SELECT internal_message_id, external_message_id, rc_id, state, date_time
FROM semd
order by date_time desc
LIMIT 3
```

| internal_message_id                  | external_message_id                  | rc_id         | state | date_time                  |
|:-------------------------------------|:-------------------------------------|:--------------|:------|:---------------------------|
| 8a591cfb-65db-4437-9ac3-f28e5caa335f | ad74d2ac-64b3-4073-8ef3-0ad8bbef8ed1 | #3240:3369361 | ASYNC | 2026-05-05 18:01:36.672237 |
| ed24f08e-680c-4646-9c0a-9ead6c7b5afd | edceb313-24a0-4bf9-ac84-f77630ac9fcf | #3239:3369457 | ASYNC | 2026-05-05 18:01:36.453845 |
| c17e0105-086b-4971-849a-68f1654d170e | cd40bfc4-3d3d-4130-ae7d-16b4411db5c3 | #3238:3369556 | ASYNC | 2026-05-05 17:30:04.948988 |

Поле `state` показывает только начальный статус движения СЭМД внутри `catcher`.
После того как `state` принимает значение `ASYNC`, дальнейшее движение СЭМД нужно смотреть уже через Онкор API.

Поле `rc_id` из таблицы `semd` содержит идентификатор задачи обработки СЭМД в Онкор.
Именно это значение нужно использовать для перехода от записи в базе `catcher` к методу `cda/get`.

_Имя `semd.rc_id` оставлено для совместимости со старой версией. Правильнее было бы назвать это поле `semd.cda_task_id`._

## Рекомендуемый порядок разбора проблемы

1. Если известны глобальные идентификаторы СЭМД (`set_id`, `id`, `version_number`), использовать `cda/search`. Это основной рекомендуемый способ поиска задачи обработки СЭМД.
2. В ответе `cda/search` найти нужную задачу обработки и проверить `cda_task_status`, `cda_task_step`, `patient_id`, `rc_cda_id`, `rc_sms_id` и `cda_task_log`.
3. Если уже известен `cda_task_id`, использовать `cda/get`.
4. Если глобальные идентификаторы СЭМД неизвестны, но известен `internal_message_id` или `external_message_id`, можно обратиться к таблице `semd` базы `catcher`, чтобы найти связанный `rc_id`.
5. Значение `rc_id` использовать как `id` в методе `cda/get`.
6. В `cda_task_log` проверить детали выполнения задачи: найден ли пациент по ФИО и СНИЛС, был ли создан новый пациент, был ли создан исходящий СЭМД и был ли он отправлен дальше.
7. По `patient_id`, `rc_cda_id` и `rc_sms_id` при необходимости открыть соответствующие объекты в интерфейсе Онкор.
